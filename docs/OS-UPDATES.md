# Updating the Base OS

How to apply Debian and kernel updates to a PixelCast device whose SD card is
protected by the read-only overlay filesystem.

**Do not just run `apt upgrade`.** On an overlay-protected device it will fill
the RAM disk, fail part-way through, and then silently discard everything it
did on the next reboot. This guide explains why, and gives the correct
procedure.

## Why `apt upgrade` fails in overlay mode

`deployment/install.sh` (step 10) configures the root filesystem as a
read-only SD card with a tmpfs overlay on top:

```text
/                    overlay   (rw)  ← what you see; lives in RAM
├── lowerdir         /media/root-ro  ← the real SD card, mounted READ-ONLY
└── upperdir         /media/root-rw  ← tmpfs, ~1.9 GB on a 4 GB Pi 4
```

Every write goes to the tmpfs upper layer and is **discarded on reboot**. This
breaks `apt` in two separate ways:

- **It runs out of space.** A full `apt full-upgrade` needs well over the
  ~1.9 GB available: the package cache alone can reach 700 MB, plus ~150 MB of
  apt lists, plus two ~37 MB RT kernels and a ~38 MB initramfs to generate.
  When it hits the wall you get half-configured packages (`dpkg -l` showing
  `iF`/`iU` states).
- **It would be pointless anyway.** Even a fully successful upgrade is thrown
  away by the next reboot, because none of it ever reaches the SD card.

### The good news about a failed upgrade

A failed `apt upgrade` in overlay mode is almost always **harmless**. The
broken `dpkg` state lives only in RAM, so a plain reboot discards it and
returns you to a known-good system. Verify the real root is clean with:

```bash
overlayroot-chroot dpkg --audit    # no output = SD card state is fine
```

### The one exception: `/boot/firmware`

`/boot/firmware` is a **vfat partition mounted read-write and is NOT part of
the overlay**. Package postinst scripts (notably `raspi-firmware`) write
there for real, even in overlay mode, and those writes survive a reboot.

So before rebooting after a failed upgrade, confirm the device can still boot:

```bash
grep -E 'kernel=|initramfs' /boot/firmware/config.txt   # expect vmlinuz-rt / initrd.img-rt
ls -l /boot/firmware/vmlinuz-rt /boot/firmware/initrd.img-rt
lsinitramfs /boot/firmware/initrd.img-rt >/dev/null && echo "initrd intact"
```

If `config.txt` still points at `vmlinuz-rt`/`initrd.img-rt` and those files
are intact, the device will boot — `kernel8.img` and the GPU firmware blobs
being newer is harmless, because `kernel=` overrides `kernel8.img`.

## What is and is not persistent

Know this before you reboot, or you will lose work:

| Location | Backing store | Survives reboot? |
| --- | --- | --- |
| `/` (most of the system) | tmpfs overlay | **No** |
| `/media/root-ro` | SD card, ro | Yes (the real root) |
| `/boot/firmware` | SD card vfat, rw | Yes |
| `/media/usb` | USB stick `pixelcast-usb`, ext4, rw | Yes |
| `/opt/PixelCast/led-signage` | SD card via `deploy.sh` write-through | Yes |

PixelCast runtime state (`playlist.json`, `users.json`, `panel.json`,
`schedule.json`) lives on the USB stick under `/media/usb/config/`, so
playlists, users and settings are **not** at risk from a reboot.

Ad-hoc changes you made by hand over SSH are a different story — see the
pre-flight audit below.

## Pre-flight: audit the RAM overlay

This is the step people skip and regret. Anything you edited by hand since the
last boot exists only in RAM. List it:

```bash
find /media/root-rw/overlay/etc -type f -o -type l
find /media/root-rw/overlay/opt -type f
find /media/root-rw/overlay/root -type f
```

Then diff anything interesting against the SD card to separate your own edits
from package/runtime noise:

```bash
diff -u /media/root-ro/etc/nginx/sites-available/PixelCast \
        /etc/nginx/sites-available/PixelCast
```

Expect to see these, which are **normal and safe to lose**:

- `/etc/fstab` — rewritten by overlayroot at every boot
- `/etc/resolv.conf`, `/etc/machine-id`, `/etc/ld.so.cache` — runtime state
- `/etc/rsyslog.d/60-forward-logserver.conf` — regenerated by
  `PixelCast-logdiscovery.service` via mDNS
- `/etc/nginx/ssl/pixelcast.{crt,key}` — restored each boot by
  `generate-ssl-cert.sh` from `/media/usb/config/ssl/`

Anything else is probably yours. Copy it somewhere persistent first, e.g.
`/media/usb/config/`, and remember `/etc/nginx/ssl/` **does not exist on the
SD card at all** — certs are re-created from the USB stick at every boot, so
a cert dropped straight into `/etc/nginx/ssl/` is RAM-only.

## The update procedure

Two reboots, roughly 15 minutes. Run everything as root.

### 1. Back up the boot files

Put them on the vfat partition, which is readable from any card reader if the
device later refuses to boot:

```bash
mkdir -p /boot/firmware/rescue
cd /boot/firmware
for f in vmlinuz-rt initrd.img-rt config.txt cmdline.txt; do
    cp -v "$f" "rescue/$f"
    cmp "$f" "rescue/$f" && echo "OK $f"
done
```

### 2. Disable the overlay and reboot

`cmdline.txt` has the **highest precedence** of all the overlayroot config
sources, so this one token is enough. Editing only
`/etc/overlayroot.local.conf` would **not** work, because the kernel cmdline
is parsed last and wins.

```bash
sed -i 's/overlayroot=tmpfs/overlayroot=disabled/' /boot/firmware/cmdline.txt
cat /boot/firmware/cmdline.txt      # sanity: still ONE line
reboot
```

`disabled` is an explicitly supported value in
`/usr/share/initramfs-tools/scripts/init-bottom/overlayroot`.

### 3. Confirm you booted writable

Do not skip this. If the overlay is still active you would upgrade into RAM
again.

```bash
mount | grep ' / '        # expect: /dev/mmcblk0p2 on / type ext4 (rw,noatime)
df -h /                   # expect ~49 G available, not 1.9 G
dpkg --audit              # expect no output
```

### 4. Decide the kernel policy

The device boots the **Debian RT kernel** (`kernel=vmlinuz-rt` in
`config.txt`), not a Raspberry Pi kernel. The `linux-image-rpi-*` packages are
therefore never booted, but still pull tens of MB into `/boot` on every
release. On a Pi 4:

```bash
# Keep the stock Pi kernel as a rescue path (boots via kernel8.img), but
# stop it churning on every upgrade:
apt-mark hold linux-image-rpi-v8 linux-headers-rpi-v8

# The 2712 packages are Pi 5 only — pure dead weight on a Pi 4:
apt-get purge linux-image-rpi-2712 linux-headers-rpi-2712 \
              'linux-image-6.*rpt-rpi-2712' 'linux-headers-6.*rpt-rpi-2712'
```

Do **not** remove `linux-image-rpi-v8`. It is the only kernel that can be
booted by commenting out `kernel=vmlinuz-rt`, which is your remote-recovery
path if an RT kernel upgrade ever goes bad.

### 5. Upgrade

`--force-confold` is important: it keeps local edits to package config files
that `install.sh` made, notably `makestep 1 -1` in `/etc/chrony/chrony.conf`
and `MODULES=most` in `/etc/initramfs-tools/initramfs.conf`.

```bash
apt-get update
DEBIAN_FRONTEND=noninteractive apt-get -y \
    -o Dpkg::Options::=--force-confdef \
    -o Dpkg::Options::=--force-confold \
    full-upgrade
```

Expect this warning if the RT kernel was upgraded — it is normal, and step 6
is the fix:

```text
WARNING: Unsupported kernel version (6.12.x+deb13-rt-arm64) - skipping setup
NOTE: Manual boot configuration may be required
```

`raspi-firmware`'s `z50-raspi-firmware` hook only handles Raspberry Pi
kernels, so it will not install the Debian RT kernel into `/boot/firmware`.

### 6. Install the new RT kernel manually

Same logic as `install.sh` step 11. **Verify the overlay module is in the new
initramfs before re-enabling the overlay** — if it is missing, the device will
boot without overlay protection (or not at all).

```bash
RT_KERNEL=$(ls /boot/vmlinuz-*-rt-arm64 | sort -V | tail -1)
RT_INITRD=$(ls /boot/initrd.img-*-rt-arm64 | sort -V | tail -1)
echo "$RT_KERNEL / $RT_INITRD"

# overlay module + overlayroot boot script must both be present:
lsinitramfs "$RT_INITRD" | grep -E 'overlayfs/overlay\.ko|init-bottom/overlayroot'

cp "$RT_KERNEL" /boot/firmware/vmlinuz-rt
cp "$RT_INITRD" /boot/firmware/initrd.img-rt
sync
cmp "$RT_KERNEL" /boot/firmware/vmlinuz-rt && echo "OK vmlinuz-rt"
cmp "$RT_INITRD" /boot/firmware/initrd.img-rt && echo "OK initrd.img-rt"
```

If `/boot/firmware` runs low on space (it is only ~510 MB), prune old
`/boot/firmware/rescue` copies rather than anything else.

### 7. Clean up

```bash
apt-get autoremove --purge
dpkg -l | awk '/^rc/ {print $2}' | xargs -r dpkg --purge
apt-get clean
dpkg --audit && echo "clean"
```

Keep the previous RT kernel installed. `autoremove` leaves it alone, and it is
your fallback.

### 8. Reboot on the new kernel while still writable

Validate the new kernel *before* going read-only, so that if something is
wrong you can still fix it:

```bash
reboot
```

Then check:

```bash
uname -r                             # new version
uname -v | grep PREEMPT_RT           # RT kernel confirmed
cat /sys/kernel/realtime             # 1
grep -o 'isolcpus=3\|iomem=relaxed' /proc/cmdline
systemctl --failed
systemctl is-active PixelCast nginx chrony
journalctl -u PixelCast -b -p warning --no-pager
```

`isolcpus=3` and `iomem=relaxed` are required for flicker-free output and for
`rpi-rgb-led-matrix` to `mmap` `/dev/mem`. If they are missing, fix
`cmdline.txt` before continuing.

### 9. Re-enable the overlay and reboot

```bash
sed -i 's/overlayroot=disabled/overlayroot=tmpfs/' /boot/firmware/cmdline.txt
cat /boot/firmware/cmdline.txt
reboot
```

### 10. Final verification

```bash
mount | grep -E 'overlayroot|root-ro'   # / is overlay, root-ro is (ro,...)
df -h /                                 # back to ~1.9 G tmpfs
cat /etc/debian_version
dpkg --audit
overlayroot-chroot dpkg --audit         # SD card state clean too
systemctl --failed
systemctl is-active PixelCast nginx chrony
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1/
```

## Alternative: `overlayroot-chroot` for small changes

For a one-off package install or config edit you do not need the reboot dance.
`overlayroot-chroot` remounts the SD card read-write and chroots into it:

```bash
overlayroot-chroot apt-get install -y some-package
```

Caveats:

- `/boot/firmware` is **not** mounted inside the chroot, so anything touching
  the kernel or initramfs will write to the wrong place. Use the full
  procedure above for kernel upgrades.
- Services cannot be restarted meaningfully from inside the chroot.
- Changes to the lower layer are not reliably visible to the running overlay
  until you reboot.

To write a single file persistently without a chroot:

```bash
mount -o remount,rw /media/root-ro
cp myfile /media/root-ro/etc/...
sync
mount -o remount,ro /media/root-ro
```

Write it to both `/etc/...` and `/media/root-ro/etc/...` if you also want it
to take effect immediately.

## Recovery if the device will not boot

Physical access and a card reader are required.

1. Mount the FAT partition (the first, ~510 MB partition).
2. Restore the previous kernel from the rescue copies:

   ```bash
   cp rescue/vmlinuz-rt    vmlinuz-rt
   cp rescue/initrd.img-rt initrd.img-rt
   cp rescue/config.txt    config.txt
   cp rescue/cmdline.txt   cmdline.txt
   ```

3. Or fall back to the stock Raspberry Pi kernel by commenting out these two
   lines in `config.txt`, which makes the firmware boot `kernel8.img`:

   ```text
   # kernel=vmlinuz-rt
   # initramfs initrd.img-rt followkernel
   ```

   Expect no RT guarantees and a flickery display, but you get a shell.

To boot writable for repairs, also set `overlayroot=disabled` in
`cmdline.txt`.

## Notes and gotchas

- **PyAV carries its own ffmpeg.** `requirements.txt` pins `av>=11.0`, and the
  PyPI wheel bundles a private ffmpeg build in `av.libs/` with hash-mangled
  sonames (e.g. `libavcodec-00f5a0ba.so.62.11.100`). PixelCast's video
  decoding therefore does **not** use the system ffmpeg, and apt upgrades to
  `libavcodec`/`libavformat`/`libswscale` cannot break or affect it. The
  trade-off: PyAV does not receive ffmpeg security fixes from apt, so refresh
  it deliberately with `pip install -U av`. Confirm which libraries are in use
  with:

  ```bash
  ldd /usr/local/lib/python3.13/dist-packages/av/video/frame*.so | grep libav
  ```

- **The clock jumps at boot.** The Pi 4 has no RTC (`timedatectl` shows
  `RTC time: n/a`), so it starts with a stale clock and chrony's
  `makestep 1 -1` steps it forward once NTP responds. A few hours of apparent
  time travel in early boot logs is expected, not a fault.

- **`systemd-remount-fs` used to report a spurious failure.** overlayroot
  writes `/media/root-ro/ / overlay ...` into `/etc/fstab`; the unit tries to
  remount `/` from it and overlayfs refuses all reconfiguration
  (`No changes allowed in reconfigure`), so it exited 1 on every boot.
  `install.sh` step 10 now installs a drop-in at
  `/etc/systemd/system/systemd-remount-fs.service.d/overlayroot.conf` setting
  `SuccessExitStatus=1`. The unit is deliberately **not** masked: with the
  overlay disabled it does real work and exits 0.

- **`/etc/nginx/ssl/` is not on the SD card.** It is populated at every boot by
  `generate-ssl-cert.sh` from `/media/usb/config/ssl/`, ordered before nginx
  by the `Requires=PixelCast-ssl-cert.service` drop-in. To install your own
  certificate persistently, put it on the USB stick and update
  `deployment/nginx/pixelcast.conf` in the repo — a device-only edit to
  `/etc/nginx/sites-available/PixelCast` is reverted by the next `deploy.sh`.

- **`deploy.sh` already handles the overlay.** It writes application updates
  through to the SD card, so normal PixelCast deployments need none of this
  procedure. See [DEPLOY_INSTRUCTIONS.md](../DEPLOY_INSTRUCTIONS.md).
